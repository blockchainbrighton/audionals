# Universal Audio Foundation Generator (v1-gemini)

## Project Overview
This project serves as the foundational definition and scaffolding for a modular synthesizer system, explicitly designed for the **blockchain** to support the music foundations of the future. It defines a library of over 144 "Atomic Elements"—irreducible, pure, and immutable audio processing components.

The goal is to create a standardized, future-proof set of DSP building blocks (Math, Logic, Memory, Oscillators, Filters, etc.) that can be used to construct complex audio systems.

## Directory Structure
The core structure is generated by `generate_foundation.sh` and organized as follows:

- **`Universal_Audio_Foundation/`**: The root of the foundation.
    - **`00_Docs/`**: Core documentation and standards.
        - `01_MANIFESTO.md`: Philosophical rules (Atomicity, Immutability, Purity).
        - `02_RUST_TRAIT.md`: The Rust `AudioNode` trait definition that all components must implement.
    - **`01_Components/`**: Contains the component definitions, grouped by category:
        - `01_Math_Atoms/` (Add, Subtract, Sin, etc.)
        - `02_Logic/` (Gates, Comparators)
        - `03_Memory/` (Delays, Buffers)
        - `04_Sources/` (Oscillators, Noise)
        - `05_Envelopes/` (ADSR, LFO)
        - `06_Filters/` (Biquad, Ladder, SVF)
        - `07_Spectral/` (FFT, Windows)
        - `08_Timing/` (Metronome, Sequencers)
        - `09_Effects/` (Clipping, Panning)
        - `10_Utils/` (Conversion, Analysis)

## Component Structure
Each component directory (e.g., `.../001_Add/`) contains:
1.  **`SPEC.md`**: The technical specification, description, and requirements for the component.
2.  **`impl.rs`**: The Rust source file where the implementation resides. *Currently, these are empty placeholders generated by the script.*

## Key Files
- **`generate_foundation.sh`**: The Bash script that defines the list of components and scaffolds the entire directory structure. Run this to reset or regenerate the tree (warning: may overwrite changes).
- **`Universal_Audio_Foundation/00_Docs/02_RUST_TRAIT.md`**: Defines the strict interface (v2.0):
    ```rust
    pub trait AudioNode {
        fn metadata(&self) -> AudioNodeMetadata;
        fn process(&mut self, inputs: &[f64], outputs: &mut [f64], sample_rate: f64);
        fn reset(&mut self);
    }
    ```

## Component Production Protocol (The "Perfect Component" Standard)

**Objective:** To implement every component in the `01_Components` directory as a flawless, 50-year-proof, blockchain-ready audio atom.

### 1. Preparation Phase
*   **Context Loading:** Read `Universal_Audio_Foundation/00_Docs/01_MANIFESTO.md` and `03_TESTING_STANDARD.md` to align with the core philosophy.
*   **Spec Analysis:** For the target component (e.g., `001_Add`), read `SPEC.md`. Understand the mathematical operation, edge cases (e.g., division by zero), and intended usage.

### 2. Implementation Phase
*   **Open the Source:** Open `impl.rs`. You will find a pre-generated struct and a `tests` module.
*   **Metadata Definition:**
    *   Populate `AudioNodeMetadata` with precise `InputDescriptor` and `OutputDescriptor` fields.
    *   Ensure names are user-friendly (e.g., "Frequency", "Gain").
    *   Set reasonable `min`, `max`, and `default` values.
*   **Logic Implementation (`process`):**
    *   **Strict Math:** Use `f64`.
    *   **Denormalization:** Before writing to output, check if the value is denormal (`val.is_subnormal()`) and flush to `0.0` if necessary, or use a conditional flush.
    *   **Safety:** Never panic. Handle `NaN` or `Inf` gracefully (clamp or zero out).
    *   **Purity:** No `print!`, no file I/O, no static mutables.
*   **State Management (`reset`):**
    *   Ensure `reset()` clears all internal buffers, delay lines, and accumulators to their initial state.

### 3. Verification Phase (The "Watertight" Guarantee)
*   **Execute Tests:** Run `cargo test` in the `Universal_Audio_Foundation` directory.
    *   *Tip:* To run tests for just one component, use `cargo test <component_name>`.
*   **Analyze Harness Results:**
    *   **Instantiation:** Did the metadata compile correctly?
    *   **Determinism:** Does running the process twice with the same input yield *identical* bits? (The harness checks this).
    *   **Denormals:** Does passing `1e-40` result in `0.0` (or safe behavior)?
    *   **Reset:** Does the component return to a clean slate?
*   **Fix Warnings:** Run `cargo check` or `cargo fix`. Zero warnings are allowed.

### 4. Finalization
*   Only when the component logic is implemented AND the harness tests pass is the component considered **Production Ready**.
*   **Log Completion:** Update `BUILD_LOG.md` by checking the box for the completed component (change `[ ]` to `[x]`).

## Maintenance
- **`GEMINI.md`**: This is the project's "Constitution". Do not modify it unless the *process* itself changes.
- **`BUILD_LOG.md`**: Update this file every time a component is successfully implemented and verified.

## Conventions
- **Language**: Rust (implied by file extensions and trait definitions).
- **Precision**: 64-bit Floating Point (`f64`).
- **Denormals**: Must be handled (flushed to zero).
- **Architecture**: Modular, stateless (where possible), and atomic.
